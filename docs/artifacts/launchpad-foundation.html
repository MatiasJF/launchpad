01

The knowledge base — the part that survives context loss

Eight files, each with one job. Two are living (rewritten as work happens), one is the boot file, the rest are reference. Together they answer: what is this, how's it going, where is what, and why is it built this way.

CLAUDE.md
Boot file

The 30-second entry point. Project in one paragraph, the golden rules, the current stack, and the exact read-order for a cold start. Every Claude reads this first. Points to everything else.

docs/STATE.md
Living

"How's it going." Current phase, what's done / in progress / next, known issues, blockers, and a last-updated stamp. Rewritten on every meaningful change — the single source of truth for status.

docs/INDEX.md
Living

"Where is what." A topic → file map: "looking for X? it's in Y." Sale settlement, the entity types, the wallet connection, the admin gate — each points to its file. Updated whenever files are added or moved.

docs/ARCHITECTURE.md
Reference

"How it's built." Module boundaries, the data-flow and settlement-flow diagrams, the hybrid operator model. Changes only when the structure changes.

docs/SCHEMA.md
Reference

The data model, in prose + types. Source of truth for the entities in §03. Mirrors the code's type definitions so the two never drift.

docs/DECISIONS.md
Living (append)

"Why it's this way." A dated decision log (ADR-style). Seeded with what we've already settled: hybrid trust, mainnet-always, STAS, BSV Desktop, no fees, admin-gating, the saleType abstraction. Append-only.

docs/ROADMAP.md
Reference

Phases & status. The plain-text mirror of the Roadmap artifact, with a status flag per phase.

docs/GLOSSARY.md
Reference

The vocabulary. STAS, UTXO, BRC-100, escrow, bonding curve, SPV, covenant — so terms mean one thing across the project.

The published artifacts
The four HTML docs (this one included) live in docs/artifacts/ and are the visual companions to the markdown KB — same information, richer form.

02

The two protocols that make it work

A knowledge base is only as good as the discipline that keeps it current. Two short rituals — one for arriving, one for leaving — do all the work.

Cold start · arriving

A fresh Claude with zero context is productive within three files.

1

Read CLAUDE.md — grasp what this is, the rules, the stack.

2

Read STATE.md — know the current phase, what's done, what's next.

3

Open INDEX.md, jump to the file for the task at hand. Working.

The guarantee: context loss costs three file reads, not a re-explanation of the project.

Definition of Done · leaving

No change is "done" until the KB reflects it. This is the self-updating mechanic.

✓

Update STATE.md — what changed, new status, any new blocker.

✓

Touch INDEX.md if any file was added, moved, or renamed.

✓

Append DECISIONS.md if a choice was made worth remembering.

✓

Sync SCHEMA / ARCHITECTURE if the model or structure moved.

Enforcement: stated as a golden rule in CLAUDE.md now; can harden into a Stop hook or PR checklist later so it's mechanical, not just habit.

03

The clean project structure

One repo, clear module boundaries. Domain logic and BSV plumbing live in packages/ so they're testable and reusable; the app is a thin shell over them. Stack: TypeScript · Next.js · SQLite (Prisma) — confirmed.

launchpad/
├─ CLAUDE.md              # boot file — any Claude starts here
├─ README.md               # human entry point
├─ docs/                   # the knowledge base (§01)
│  ├─ STATE.md  INDEX.md  ARCHITECTURE.md  SCHEMA.md
│  ├─ DECISIONS.md  ROADMAP.md  GLOSSARY.md
│  └─ artifacts/            # the published HTML docs
├─ apps/
│  └─ web/                  # Next.js: public launchpad + admin routes
│     ├─ app/(public)/       # browse, project pages, buy
│     ├─ app/(admin)/        # auth-gated: create project, approve
│     └─ app/api/            # backend: sequencing, settlement
├─ packages/
│  ├─ core/                # domain: entities, sale logic, state machine
│  ├─ bsv/                 # STAS issuance, settlement, SPV, BRC-100 wallet
│  ├─ db/                  # Prisma schema + SQLite → Postgres (§04)
│  └─ shared/              # types, config, utils
├─ .env.example
└─ package.json

Why the split: core/ and bsv/ hold the logic that's hard to get right and must be tested in isolation. The Next.js app stays a shell — swappable, and never the place business rules hide.

04

The project / entity schema

Six entities. Two design choices from the Vision Map are baked in from day one: Sale.type (the instant | escrow-presale abstraction) and Order.state (which carries refunded / withdrawn — the hold-and-return settlement). Nothing to rewrite when the future layers arrive.

Order

* → 1 Sale
  • idpk
  • saleId→Sale
  • buyerIdentitypubkey
  • kindbuy·contribute
  • tokens · satsPaidint
  • statepending→settled
  • state·refunded·withdrawn

Event

append-only ledger
  • idpk
  • entity · entityIdref
  • typestr
  • actor→Account
  • payloadHashon-chain

The chain of custody: Account → Project → Token → Sale → Order, with Event as an append-only audit log whose payloadHash can be anchored on-chain — so the off-chain database stays tamper-evident against the mainnet record.
