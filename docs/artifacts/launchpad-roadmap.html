The thesis

Build the offering engine excellently; defer the AMM.

BSV is genuinely well-suited to the issuance → sale → distribution half of a launchpad — that half is just structured UTXOs, and it plays to the chain's strengths: cheap, scalable, SPV-verifiable. The AMM / farm / vault half fights the grain of the UTXO model and should be prototyped later, kept partly operator-mediated for a long time.

The reference platforms — DAO Maker, Binance Launchpool, PinkSale, DxSale — were all built for account-based chains with Turing-complete smart contracts. Their feature lists assume a shared, mutable, global pool state that every user can call at once. BSV has no such thing. Don't let their feature lists set our scope: the offering engine is ~80% of the value and ~40% of the difficulty.

The core constraint

No global mutable state

Everything downstream follows from this. On BSV we work with:

  • UTXOs — discrete coins, each spent exactly once. No mutable account balances.
  • STAS — a token protocol where each token amount lives inside a UTXO with a colored-coin script. Total supply is minted at issuance; a "transfer" spends STAS UTXOs and re-creates them under the protocol rules.
  • BRC-100 — the wallet↔application interface standard (what Metanet Desktop and compatible wallets expose). This is our "connect wallet" layer — an interface protocol, not a token or DeFi standard.
  • sCrypt / Bitcoin Script — on-chain enforcement (covenants), with overlay services (BRC-22/24) to index and track our app's UTXO set.
Design consequence

Any feature that needs "many users hitting one pool at once" — an AMM, a bonding curve, a staking vault — becomes a single-UTXO-contention problem: only one party can spend the pool UTXO per step. This is solved with transaction chaining, operator sequencing, or off-chain matching with on-chain settlement. It is the central engineering decision of the entire project, and everything else is anchored on it.

Decision · locked

Trust model: hybrid, operator-settled

Token issuance, sale settlement, and user holdings are all real on-chain STAS UTXOs (independently verifiable). The matching & pricing engine is our backend. We publish enough on-chain that a user can verify they got what they paid for — then migrate individual primitives to full covenants over time.

System shape

Five moving parts

Public launchpad

React/Next app. Connect via BRC-100 wallet, browse projects, view tokenomics & info, buy tokens. Buys are transactions the user's own wallet signs — non-custodial.

Project / issuer panel

Authenticated dashboard: define supply (total + public), price, sale window, vesting; submit team, docs, links, logo. Emits a STAS issuance tx + sale config.

Curation & admin

Platform reviews/approves listings before they go public. Also our legal and anti-scam gate — non-optional given the reputational surface.

Backend + overlay

Indexes STAS UTXOs, tracks sale state, sequences purchases, serves the API. Off-chain metadata anchored on-chain by hash so it's tamper-evident.

Settlement engine

Builds STAS transfer + payment transactions, broadcasts via ARC, verifies with SPV. The bridge between backend intent and on-chain truth.

Not from zero

Several MCP servers and agents already wired into this environment target exactly this: STAS/BTMS token handlers, wallet setup, overlay nodes, SPV verification, and script templates. The plumbing has strong starting points.

Pricing

Fixed price now, bonding curves as a study track

Fixed price (MVP). A project sets X sats per token. We pre-split the public allocation into STAS UTXOs; a buy is "user pays X, receives tokens, change returns to the pool." Predictable and simple to settle.

Bonding curves (design now, ship later). A bonding curve makes price a deterministic function of supply sold — price rises as tokens are bought, falls on sell-back — so the curve is the market maker, no counterparty needed. Common shapes:

  • Linear — price = m·sold + b. Easy to reason about.
  • Exponential — price = b·e^(k·sold). Rewards early buyers hard; can feel predatory.
  • Constant-product (x·y=k) — the Uniswap model; a reserve of tokens and a reserve of sats, price = ratio. Best-understood for a two-sided market.
The BSV catch

A bonding curve is a stateful contract — it must remember sold. On UTXO that's a single "curve UTXO" spent-and-recreated on each trade, which serializes trades and needs either an sCrypt covenant enforcing the math on-chain, or an operator enforcing it and settling verifiably. Recommended path: launch fixed-price → model the curve off-chain (operator-enforced, published state) → harden into an sCrypt covenant once proven. Curves also invite front-running/MEV — study the failure modes before committing.

DeFi primitives against the UTXO model

How well each requested primitive fits BSV, and how it's built. Fit degrades as a feature needs shared concurrent pool state.

Cross-cutting · every phase

Security, legal & anti-scam curation

A launchpad handles other people's money and lists strangers' tokens — that is the reputational and legal center of gravity, not an afterthought. PinkSale's reputation is the cautionary example. At BSVA this routes through the proper classification and legal process early: listing review, issuer KYC posture, disclaimers, and a clear line on what the platform does and does not vouch for.
