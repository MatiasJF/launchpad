01

The fork hiding inside "buy tokens"

The reference launchpads and our MVP share the word "sale" but are two different products. Which one we mean decides the entire settlement layer — and whether features like emergency withdraw are even meaningful.

Our MVP Instant swap

Pay, receive, verify — all in one transaction.

  • Buyer pays and holds the token immediately
  • Has a price; no cap, no timer, no finalize
  • Every buy is complete on its own — nothing pooled
  • Can't fail; there is nothing to refund
Emergency withdraw — meaningless here. You already hold the token; there's nothing escrowed to pull back.

Their model Escrow presale

Contribute to a pool now, settle at the end.

  • Buyer contributes to a pool; receives nothing yet
  • Runs to a soft/hard cap on a timer, then finalizes
  • Success → claim tokens; failure → everyone refunded
  • Funds sit in escrow between contribute and finalize
Emergency withdraw — a symptom of escrow. Bail out mid-sale for a penalty fee (free once a sale has already failed). The fee just stops last-minute exits collapsing a near-cap sale.
Why this is good news on BSV

Escrow maps cleanly to UTXO. A contribution is a discrete, traceable coin the operator (or a covenant) can only forward-to-project on finalize or return-to-buyer on refund. A refund is just returning that UTXO — no shared pool balance to get wrong. "Building for the future" means designing settlement to hold-and-return, not fighting the chain.

02

The layer stack

Every future feature grouped by what it actually depends on. Note the shape: the layer that makes it look like a mature launchpad (L1) is the cheapest, and only one heavy layer (L2) changes the settlement core.

L0

Instant swap

Ship now · MVP

Pay a fixed price, receive STAS tokens, SPV-verify — on mainnet, gated by admin auth. The spine everything else attaches to.

depends on → nothing · this is the foundation
L1

Project surface

UI-only · non-gating

Project pages, docs, metrics, charts, dashboards, "my holdings" / portfolio. This is where it starts to look like a real launchpad — and it's the cheapest layer, pure UI over a good data model. Build incrementally, anytime.

depends on → a rich project/entity schema
L2

Escrow presale

Settlement core

Soft/hard caps, timers, finalize, refunds — and only now does emergency withdraw become meaningful. The one genuinely heavy future layer; it changes how settlement works, not just the UI.

depends on → hold-and-return settlement
L3

Identity & allocation

Future

Tiers, per-wallet caps, whitelists, KYC posture. On BSV these can be genuinely verifiable via wallet-native identity rather than a database flag — a strength, not just a port.

depends on → BRC-100 certificates / paymail identity
L4

Distribution

Future

Vesting UI (timelocked tranches made visible), airdrop claims via Merkle proof, community allocations.

depends on → timelocks + claim mechanics
L5

Rewards & market

Far future

Staking → bonding curves → farms → vaults. The hard tail, where UTXO contention bites; kept partly operator-mediated for a long time.

depends on → overlay accounting + sCrypt covenants
03

Three decisions to make now — free at MVP, expensive later

None of these add work to the first build. They keep the layers above from forcing a rewrite when we choose to reach for them.

DECISION 1

A sale-type abstraction

Model saleType: instant | escrow-presale from day one, even if only instant is implemented. L2 then slots in as a new type, not a rebuild.

DECISION 2

Hold-and-return settlement

Design the settlement layer so it can hold a contribution and return it — not only deliver tokens. Escrow, refunds & emergency withdraw become later configurations of one engine.

DECISION 3

A rich project schema

Give each project enough structured data — team, docs, links, media, metrics anchors — to hang all of L1 off later. The entire "looks mature" layer is then additive UI.

04

Don't cargo-cult — three EVM features, translated

Some headline features of those platforms are EVM-shaped and don't port 1:1. Copying the mechanism is a mistake; answering the same question the BSV way is the goal.

Their featureWhat it really answersThe BSV translation
Liquidity locking / auto-LP "Can the team rug the liquidity?" → No AMM means no LP token to lock. Answer it instead with verifiable, disclosed treasury & vesting timelocks on-chain.
Tiers + KYC gating "Who's allowed, and how much?" → Wallet-native identity (BRC-100 certificates, paymail) can make tiers genuinely verifiable rather than a DB flag.
Refund / insurance guarantees
(SHO refund, DYCO)		 "What if the project underdelivers?" → Rides on the escrow model + treasury-backed refunds (L2/L3). Note as a trust feature, not an MVP item.
The through-line

Build L0 dumb-simple. Make the three decisions above so L1–L5 stay additive. Translate EVM features to the question they answer, not the mechanism they use. That's how the first approach stays simple and the future stays reachable.
